# Security boundary

All API routes require the same administrative bearer token (minimum 32 characters; generate 32 random bytes). There is no multi-user authorization, tenant separation, token revocation list or hostile-worker trust boundary. Anyone with the token can submit jobs to every enabled worker and inspect metadata/logs. New profiles and invitations are mode-0600 files, and initialization creates private local state without printing the token. Invitations grant full administrative access; they are neither scoped nor expiring. Keep environment-based tokens in mode-0600 files; `--token` is available but may appear in process listings. The known RUNSPK_TOKEN environment variable is removed from job launch environments. Do not put credentials in command arguments or output.

The scheduler binds loopback only. Use SSH local forwarding between machines, or an authenticated TLS terminator on the scheduler host. The client rejects remote plaintext HTTP, disables redirects and retains certificate verification. SSH host keys and HTTPS certificate verification are part of the deployment trust boundary. Never publish the loopback listener through an unauthenticated forwarding service. Rotate a token by restarting scheduler and workers together.

History pruning uses the same administrative API token and cannot remove active/uncertain work, keyed jobs or unfinished execution receipts. The local `runspk backup` command uses filesystem permissions rather than API authentication; snapshots contain commands and captured output and are created mode 0600 without overwriting existing files. Project inputs and declared outputs are also stored in the database. Exclusions and safe path traversal prevent common accidental credential uploads and link escapes, but are not a secret scanner or sandbox; review the dry-run manifest. Protect scheduler databases, backups and worker journals with the same account boundary.

## Native backend

Submission requires `--trusted` and the worker requires `--allow-native` (embedded `--local` is explicit native consent). Native workers refuse root execution. Use a dedicated unprivileged account, including restricted file permissions. Jobs inherit the account's other environment variables, filesystem and network access. They can read account-accessible files, fork, use network services or deliberately escape process groups. Native execution is unsuitable for arbitrary untrusted code.

CPU affinity assigns disjoint logical CPU identities within one worker. Trusted native code can change its own affinity, so this remains a cooperation boundary. RLIMIT_AS limits each process's virtual address space, not the aggregate RSS of a process tree. Process groups, no-new-privileges, disabled core dumps and GNU timeout address accidents in cooperating workloads. These are not a sandbox. Overlapping worker affinity pools or other host applications can contend with reservations. GPU visibility variables are advisory for native jobs, not device access controls.

## Container backend

Enable `--runtime docker` or `--runtime podman` on the worker, preload images, and submit with `--image IMAGE`. The scheduler passes argument arrays and overrides image entrypoint. The fixed worker launch gate uses a constant shell script; job arguments are never interpolated into that script.

Containers run as UID/GID 65534, with no network, no host mounts, a read-only root filesystem, a 16 MiB noexec tmpfs, an 8 MiB shared-memory segment, no Linux capabilities, no-new-privileges and a 128-PID limit. CPU/memory cgroup limits are mandatory, and memory-swap equals memory to disallow swap. Unsupported limits fail the job rather than falling back to native execution. Docker's default seccomp/AppArmor settings remain in force. Image pulls are disabled during execution; use trusted, preferably digest-pinned, preloaded images. Package inputs in the image; container output is logs or application-managed output, with no host volume API.

Containers share the kernel and are not VMs. Docker daemon membership grants powerful host access to the worker account; do not expose its socket to jobs. Prefer rootless deployment where supported. Physical GPU support needs the NVIDIA Container Toolkit already installed by the administrator. Podman CPU containers are implemented but not hardware-tested here; physical GPU container requests currently require Docker.

Container names and ownership labels derive from attempt UUIDs, recorded before launch. Cancellation, timeout and restart recovery force-remove the matching container after verifying its ownership label. A cleanup failure retains the attempt for reconciliation and keeps its reservation. If the worker is killed, an existing container can continue until worker recovery or operator fencing; the timeout of a dead Docker CLI cannot stop a daemon-owned container. Cgroups still constrain it and its reservation remains held. Keep workers supervised and preserve their journals.

References: [Docker resource limits](https://docs.docker.com/engine/containers/resource_constraints/), [run security flags](https://docs.docker.com/engine/containers/run/), [GPU visibility](https://docs.docker.com/engine/containers/gpu/). No automatic system-wide cgroup, driver, container-runtime or firewall configuration is performed.

Project transfer limits, no-overwrite extraction, per-attempt ownership and recovery are documented in [WORKSPACES.md](WORKSPACES.md). Native code and authenticated workers remain trusted; a shared token cannot provide confidentiality between team members.

Scheduler URLs reject embedded credentials, queries and fragments; bearer credentials stay in private profiles/environment. HTTP error bodies redact the active bearer token before CLI/TUI diagnostics. Snapshot deserialization enforces the hard file-count ceiling before constructing an arbitrarily large file list. The monitor sanitizes control sequences in all rendered API text. Host telemetry is an authenticated worker observation for display only, not a resource accounting authority.
